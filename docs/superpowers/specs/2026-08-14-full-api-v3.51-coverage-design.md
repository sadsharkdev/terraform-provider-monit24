# Design: Full Monit24 API v3.51 coverage + token authentication

## Context

The provider was last released tracking a ~2022 (v3.27-era) snapshot of the Monit24 API. A prior audit (this session) brought three existing resources up to date and added `monit24_periodic_report_address`, `monit24_suspension`, `monit24_weekly_suspension`, `monit24_group_share` (branch `feature/monit24-api-v3.51-resources`, commit `b157cee`) and `monit24_subaccount` (branch `feature/monit24-subaccount-resource`, commit `fb15f07`, built off `main` independently).

This spec covers finishing the job: consolidating that work onto one branch, fixing two known gaps in it, adding full CRUD coverage for every remaining writable subsystem in the API, adding data sources (paired with resources, and for read-only reference/dictionary data), and fixing a real authentication bug — the provider cannot talk to any Monit24 account that has 2FA enabled, because it only supports HTTP Basic Auth.

Everything lands as a sequence of commits on the single existing branch `feature/monit24-api-v3.51-resources`, so it becomes one upstream MR to `monit24/terraform-provider-monit24`.

## Goals

1. One branch, many commits, one eventual upstream MR — no branch-per-feature.
2. Resources cover the full **writable/editable** surface of the API, with two explicit, justified exclusions (`reports`, `corrections` — no natural Terraform "current state"; `sessions` — would require embedding a password to create, redundant with existing auth).
3. Every meaningfully "primary" resource gets a paired data source (get-by-id); high-value read-only reference data (service types, notification channels, sensors, etc.) gets its own data source even without a backing resource.
4. Fix the 2FA/Basic-Auth authentication gap via a `MONIT24_TOKEN`-driven Bearer-token auth mode, verified working by the user against the live API.
5. Two specific technical debts from the prior session get resolved or at least conclusively tested: `monit24_subaccount`'s `parent_account_id` inference assumption, and `monit24_service`'s previously-excluded `is_archived` field (now in scope under "full coverage").

## Non-goals

- `reports`, `corrections`: generate-once / point-in-time API objects, no convergeable state, poor fit for Terraform's plan/diff model. Not resources.
- `sessions`: `POST /sessions` requires `username`+`password` to mint a new session — a Terraform resource that creates one would need the same secret the provider's own Basic Auth already uses, with no benefit. Not modeled. (Note: this is distinct from the *authentication* use of an already-existing token, which Goal 4 does add support for.)
- `admin/*` tag: Monit24-staff-only API surface, not reachable by ordinary customer credentials. Out of scope regardless of "full coverage."
- Every one of the ~19 `dictionaries/*` categories does not get a data source in this pass — only the ones actually referenced as string/int IDs elsewhere in the schema (see Data sources section). The rest (languages, artifact_types, report_attachment_types, report_sections, report_template_variables, template_variables, reporting_plans, service_type_categories) are deferred; same pattern applies later if needed.
- No data sources for child/junction-style records (suspensions of any kind, `group_share`, `user_data_setting`) — low value to look up standalone by ID.

## Branch & commit strategy

- Stay on `feature/monit24-api-v3.51-resources` (currently: `b157cee` on top of `main`).
- Cherry-pick `fb15f07` (the `monit24_subaccount` commit, currently sitting on the now-abandoned `feature/monit24-subaccount-resource` branch) onto this branch as the next commit.
- All further work (auth fix, account-family fixes, each subsequent phase below) lands as its own logical commit(s) on this same branch — small enough to review, not squashed into one giant commit.
- The two old branch names (`feature/monit24-api-v3.51-resources` stays; `feature/monit24-subaccount-resource` becomes obsolete after the cherry-pick) — don't delete `feature/monit24-subaccount-resource` without being asked.

## Authentication fix (Bearer token support)

Verified against live docs (`conventions.html`, `quickstart.html`) and confirmed working by the user against the real API:

- Basic Auth (`user:pass`) only works when the account has **no** 2FA configured.
- For 2FA-enabled accounts, the API requires a token, sent as `Authorization: Bearer <token>` — **not** as the username or password slot of a Basic auth header (this is why `MONIT24_USER`+`MONIT24_PASSWORD` set to `user:token` doesn't work today).
- Tokens are created via the Monit24 account UI (or `POST /sessions` with `username`+`password`, returning `{"id": ..., "token": ...}` — but the UI path is what the user uses in practice).

Design:
- `client/client.go`: `Client` gains a `token` field alongside the existing `basicAuth` field (mutually exclusive — only one is ever set). `rawRequest` sends `Authorization: Bearer <token>` when `token` is set, `Authorization: Basic <basicAuth>` otherwise. Add `NewTokenClient(ctx, token string) (Client, error)` alongside the existing `NewBasicAuthClient`, both resolving `OwnerID()` the same way via `GET /accounts/my_account` (auth-mechanism-agnostic).
- `monit24/provider.go`: new schema field `token` (`Optional`, `Sensitive`, `DefaultFunc: schema.EnvDefaultFunc("MONIT24_TOKEN", nil)`).
- `providerConfigure`: precedence — if `token` is set, use `NewTokenClient` (user/password ignored entirely, matching the user's explicit ask: "auth bedzie tylko po tym tokenie"). Else if `user`+`password` are set, use the existing Basic Auth path. Else, the existing "no credentials provided" error.
- Update `README.md` and `CLAUDE.md` with a `MONIT24_TOKEN` example and a note that 2FA-enabled accounts must use it instead of `MONIT24_USER`/`MONIT24_PASSWORD`.
- Acceptance tests: existing `preCheck` requires `MONIT24_USER`/`MONIT24_PASSWORD`; this doesn't change (token auth is an alternative, not a replacement, for local/dev testing convenience it's fine for testacc to keep using Basic Auth as today).

## Account-family fixes (carried over from `monit24_subaccount`)

- **`parent_account_id`**: cannot be conclusively fixed without live API access. Harden `resource_subaccount_test.go` to assert its value precisely (not just `TestCheckResourceAttrSet`) so the next real `make testacc` run conclusively proves or disproves the "inferred by API" assumption; document both outcomes and the one-line fix (`Optional`+settable) in `CLAUDE.md` if the assumption turns out wrong.
- **`monit24_service.is_archived`**: re-add as `Optional bool` (was deliberately excluded before; now in scope under "full API coverage"). Flag for live-API verification of write semantics, same treatment as `parent_account_id`.
- **`user_data` split**: `PUT /user_data/{id}` exists independently of subaccount creation — the prior session's `ForceNew` on the whole `user_data` block in `monit24_subaccount` was overly restrictive. Add a standalone `monit24_user_data` resource (keyed by the same numeric account `id`) that manages `address`/`contact_person`/`phone_number`/`tax_identification_number`/`ip_whitelist`/`ip_whitelist_enabled`/`email_address` post-creation via PUT. `monit24_subaccount.user_data` remains as-is (required at creation, `ForceNew`) since the API mandates it there; real day-2 updates go through the new resource instead.
- **`monit24_account_user`**: `POST /accounts` (adds another login to the *same* account — distinct from `monit24_subaccount`'s `POST /accounts/subaccount`, which creates a dependent account). Same underlying shape as subaccount minus the subaccount-only fields (`set_password_url`, `subaccount_block`, `subaccount_edit`, `is_2fa_setup_required`). In scope now under "full coverage."
- **`monit24_user_data_setting`**: generic per-account key/value store (`PUT/GET/DELETE /user_data/{id}/settings/{key}`), value typed as an arbitrary JSON-ish string (API schema is `any`).

## Phased resource + data source rollout

Each phase = resource(s) and their paired data source(s) delivered together, as its own commit or small commit group. Order matters where phases reference each other's dictionary values in examples.

**Phase 1 — Dictionary data sources** (no resource dependencies, used by later phases' examples)
`monit24_service_type`, `monit24_notification_channel`, `monit24_notification_condition`, `monit24_notification_mode`, `monit24_recovery_notification_mode`, `monit24_sensor`, `monit24_contact_channel`, `monit24_metric_type`, `monit24_error_type_category` — each a simple get-by-id data source over the corresponding `dictionaries/*` endpoint.

**Phase 2 — Account family** (the fixes above, bundled as their own phase)
`monit24_service` (`is_archived`), `monit24_subaccount` (`parent_account_id` test hardening), `monit24_user_data`, `monit24_account_user`, `monit24_user_data_setting`. No data sources planned for these (account objects are typically referenced by ID the caller already has, e.g. from `monit24_subaccount.x.id`).

**Phase 3 — Contacts family**
Resources: `monit24_contact`, `monit24_contact_address`, `monit24_contact_group`, `monit24_contact_suspension`, `monit24_contact_weekly_suspension`.
Data sources: `monit24_contact`, `monit24_contact_group` (get-by-id only).

**Phase 4 — Events + Escalations family** (largest, most complex — depends on `contact`/`contact_group` existing for escalation assignment examples)
Resources: `monit24_event`, `monit24_escalation`, `monit24_escalation_suspension`, `monit24_escalation_weekly_suspension`.
Data sources: `monit24_event`, `monit24_escalation`.

**Phase 5 — Reporting family**
Resources: `monit24_report_template`, `monit24_template` (custom notification templates).
Data sources: `monit24_report_template`, `monit24_template`.

**Phase 6 — Companion data sources for pre-existing resources**
`monit24_group`, `monit24_service`, `monit24_notification_address`, `monit24_periodic_report_address`, `monit24_subaccount`, `monit24_account_user` — get-by-id, closing the gap for resources built before this "pair every resource with a data source" rule existed.

## Implementation pattern (established, reused throughout)

Every resource: `client/<name>.go` (struct with JSON tags + `Create*`/`Read*`/`Update*`/`Delete*` methods mirroring `client/group.go`) + `monit24/resource_<name>.go` (schema + CRUD context functions mirroring `resource_notification_address.go` for simple resources or `resource_service.go` for resources with many optional fields) + `monit24/resource_<name>_test.go` (acceptance test) + `examples/resources/monit24_<name>/{resource.tf,import.sh}`, registered in `monit24/provider.go`'s `ResourcesMap`. IDs stored via `strconv.Itoa`/`strconv.Atoi`; 404 → `d.SetId(""); return nil` on Read; import via `schema.ImportStatePassthroughContext`; optional/nullable API fields as pointers, only `d.Set` when non-nil.

Every data source: `monit24/data_source_<name>.go`, `Schema` mirrors the resource's but all fields `Computed` except an `id` (or lookup key) that's `Required`, single `ReadContext` that calls the same `client.Read<Name>` method the resource already uses (no new client code needed for get-by-id data sources), registered in `Provider().DataSourcesMap`.

## Testing & verification

- `gofmt -l -w`, `go build ./...`, `go vet ./...`, `go test ./...` after every file, same as prior sessions.
- No live `MONIT24_USER`/`MONIT24_PASSWORD` credentials available in this environment — acceptance tests are written but will show as skipped locally; every place behavior is inferred rather than confirmed from the OpenAPI spec gets an explicit flag in `CLAUDE.md` (matching the existing `parent_account_id` / subaccount-delete-vs-close precedent) and, where feasible, an acceptance-test assertion strong enough to catch it the first time `make testacc` actually runs.
- `make docs` — same pre-existing local blocker as before (this machine's `tfenv` has no resolvable Terraform version and `tfenv use` fails without GNU grep); flag as still-blocked, don't silently skip mentioning it.

## Scale note

This is a large body of work — 6 phases, roughly 15 new resources and 20 new data sources plus the auth fix and account-family fixes. Realistically spans many implementation sessions, not one. The plan produced from this spec should reflect that (explicit phase checkpoints, not one monolithic task list).
